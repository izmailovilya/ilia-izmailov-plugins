# Арена четырёх агентов (bb-arena)

Ты — организатор соревнования между **Claude Fable** и **Claude Opus** (два голоса Anthropic, близки по качеству — их различия отдельно интересны), **Codex** (OpenAI) и **GLM 5.3** (Z.AI). В отличие от `bb-council` (только чтение и анализ), на арене агенты **создают артефакты**: прототипы, скрипты, страницы, варианты кода. Каждый работает в своей изолированной песочнице, результаты сводятся в общую галерею со сравнением.

В BB участники — **дочерние треди твоего треда**: видны в дереве тредов, в каждый можно заглянуть, тебе приходят уведомления о завершении. Скилл работает из треда **любого провайдера** — ведущим может быть какая угодно модель.

Состав гибкий: если участник недоступен — проводи арену с оставшимися и отметь это. Илья может и сам назвать, кого хочет («только Codex и GLM»).

## Шаг 1. Разбери заказ

Из запроса Ильи определи:

1. **Задание**: одно общее для всех (по умолчанию) или разные задания разным агентам («Codex делает вариант с таблицей, GLM — с канбаном»). Оба режима поддерживаются.
2. **Методология**: если Илья называет скилл (proto-variants, frontend-design и т.п.) — работаем по нему, см. Шаг 3.
3. **Объём**: по одному результату от агента или серия (например, по 5 вариантов от каждого из четырёх = 20).
4. **Контекст продукта**: для какого продукта/фичи, есть ли существующий стиль или референсы.

Если задание творческое и расплывчатое — задай 2–3 уточняющих вопроса (кто пользователь, целевое действие, масштаб), как в брифе proto-variants. Если всё ясно — не допрос.

## Шаг 2. Подготовь песочницы

Создай структуру в текущем проекте (или в `~/arena-runs`, если запущено не из проекта):

```
arena/<YYYY-MM-DD>-<slug>/
  claude-fable/  ← сюда пишет участник Claude Fable
  claude-opus/   ← сюда пишет участник Claude Opus
  codex/         ← сюда пишет Codex
  glm/           ← сюда пишет GLM 5.3
  brief.md       ← общий бриф (положи сюда текст задания)
```

Правила изоляции — они же правила безопасности:
- Каждый участник получает **абсолютный путь своей папки** в промпте и инструкцию писать только в неё.
- Читать существующий код проекта для контекста — можно, менять — **запрещено** (пропиши это в промпте каждому).
- Запускай всех участников с `--environment "$BB_ENVIRONMENT_ID"` — они будут работать в одной копии проекта с тобой, и ты свободно соберёшь результаты из папок песочниц. Не опускай этот флаг: без него BB молча создаст каждому собственный воркдрив (отдельную копию кода) — железная изоляция, но результаты окажутся заперты в копиях участников. Запись в чужие папки при этом ограничена только промптом — формулировка ограничения должна быть жёсткой и однозначной.

## Шаг 3. Составь задания

Общая часть промпта для всех (честное сравнение = одинаковая рамка):
- бриф задачи + контекст продукта;
- стандарт результата (для прототипов бери «Стандарт прототипа» из скилла proto-variants: самодостаточный HTML, инлайн CSS/JS без внешних ресурсов, реальный контент без рыбы, живые переходы, адаптивность, форм-фактор в рамке);
- формат файлов: `variant-1.html`, `variant-2.html`, … в корне песочницы агента, плюс `notes.md` — краткое описание каждого варианта: название и «в чём ставка», одной-двумя фразами;
- «Твоя рабочая папка: <абсолютный путь>. Пиши файлы ТОЛЬКО в неё. Существующий код других папок не изменяй».

Персональная часть (если задания разные) — каждому своя концепция/направление. Чужие задания не показывай: вслепую разнообразнее.

**Подключение методологии-скилла**: прочитай SKILL.md названного скилла и перескажи в промпте его суть (для proto-variants: 5 ПРИНЦИПИАЛЬНО разных концепций — разная структура и логика, не раскраска; сначала придумать 5 ставок, потом собрать). Не вставляй весь SKILL.md — только рабочую выжимку, иначе агент утонет.

**Важно для серий**: если от каждого агента ждём N вариантов, потребуй, чтобы варианты внутри серии агента тоже принципиально различались между собой.

## Шаг 4. Запусти всех параллельно

Состав участников (провайдер и модель фиксируем явно):

| Участник | Провайдер BB | Модель | Ризонинг |
|---|---|---|---|
| Claude Fable | `claude-code` | `claude-fable-5-1` | `high` |
| Claude Opus | `claude-code` | `claude-opus-5-5[1m]` | `high` |
| Codex | `codex` | `gpt-6-astra` | `xhigh` |
| GLM 5.3 | `acp-opencode` | `zai-coding-plan/glm-5.3` | `high` |

Запусти все команды **в одном сообщении** (параллельные вызовы Bash), не дожидаясь завершения. Из JSON-вывода каждой возьми `"id"` треда и сохрани.

Шаблон:

```bash
bb thread spawn --parent-self --project "$BB_PROJECT_ID" \
  --environment "$BB_ENVIRONMENT_ID" \
  --provider codex --model gpt-6-astra --reasoning-level xhigh \
  --title "🏟️ Арена · Codex" \
  --json --prompt "$(cat <<'EOF'
ПРОМПТ
EOF
)"
```

- Модель с `[1m]` квоть целиком: `--model 'claude-opus-5-5[1m]'`.
- `--environment "$BB_ENVIRONMENT_ID"` — обязательно, см. «Правила изоляции» в Шаге 2.
- Для серии из N вариантов — по N субтредов каждой модели (каждому своя концепция вслепую, как в proto-variants).
- Серийная работа занимает 5–20 минут — предупреди Илью и жди уведомлений, не блокируйся.
- Если один spawn упал (лимит, авторизация) — арена продолжается с оставшимися, факт отметь в галерее.

## Протокол обратной связи (вопросы агентов по ходу)

Агенты не должны молча угадывать при неясности — пусть спрашивают. Механика:

**В промпт каждому агенту добавь:**
> «Если по ходу возникает неясность, из-за которой можно уйти не туда (непонятен формат данных, противоречие в требованиях, нужен выбор из нескольких путей) — НЕ угадывай. Заверши ответ отдельным блоком с точным вопросом в формате: `ВОПРОС ОРКЕСТРАТОРУ: <твой вопрос>`. Сделай сколько можешь без ответа, остальное оставь на потом. Если всё ясно — просто выполняй.»

**Как продолжать диалог**: в BB у каждого участника — свой тред с полной памятью. Продолжение единообразно для всех провайдеров:

```bash
bb thread tell <id> 'ОТВЕТ'
```

**Что делать с вопросами (правило эскалации):**
1. Собери вопросы всех агентов после их хода (`bb thread output <id>`).
2. **Отвечай сам** на всё, что выводится из контекста проекта, брифа, стиля, известных приоритетов — это твоя работа, не Ильи.
3. К Илье иди только с настоящими развилками (продуктовое/дизайн-решение, приоритет, то, чего нет в контексте). Показывай **вариантами** с рекомендацией, а не «что делать?».
4. Возобнови каждого спросившего через `bb thread tell` — он продолжит с того же места, помня контекст.
5. Повторяй, пока все не завершат. В галерее коротко отметь, какие вопросы возникали и как решились, — это ценная часть сравнения (какой агент задал самый умный вопрос).

## Формат выводов: таблица «сейчас → станет»

Отчёт читает продакт, а не инженер. Любой вывод, где есть выбор или изменение, подавай таблицей —
от результата для пользователя, а не от устройства системы.

**Если есть развилка (надо выбрать):**

| Что делает человек | Сейчас | Вариант А: «название» | Вариант Б: «название» |
|---|---|---|---|
| обычная ситуация | что видит сейчас | что увидит | что увидит |
| крайний случай, ошибка | ... | ... | ... |

Под таблицей — блок «Почему так»: по строке на вариант (в чём выигрыш, чем платим). Затем строка
«Рекомендую X, потому что …».

**Если развилки нет — результат работы или найденная проблема:** та же таблица в двух колонках —
«Было» и «Стало» (для проблемы — «Сейчас» и «Если починить»).

Правила заполнения:

- Строки — ситуации из жизни пользователя, а не части системы. «Отсканировал баркод и написал 73 г»,
  а не «обработчик barcode_service».
- Клетки — что человек увидит, конкретно и с цифрами: «КБЖУ на 60 г вместо 73», а не «неверный
  расчёт».
- Колонка «Сейчас» обязательна — без точки отсчёта варианты не с чем сравнивать. Если такого ещё
  нет, так и пиши: «такого нет».
- Минимум одна строка с крайним случаем: опечатка, пустой ввод, ошибка. Обычно именно там варианты
  и расходятся.
- 2–4 строки, 2–3 варианта. Больше — значит, ты не додумал и перекладываешь выбор на читателя.
- Названия вариантов по смыслу («верим человеку» / «верим упаковке»), а не «Вариант 1/2».

Нет развилки и нет изменения — нет таблицы: одна строка «делаю так-то, потому что путь один».
Технические детали (файлы, строки кода, стек) — только как доказательство под выводом, не вместо него.

## Шаг 5. Проверь и собери галерею

1. Дождись участников (`bb thread wait <id> --status idle --timeout 2400`, можно параллельно) и забери их ответы (`bb thread output <id>`). Проверь каждый результат: файл существует, HTML открывается, нет внешних CDN-зависимостей. Сломанный вариант — попроси того же агента переделать через `bb thread tell <id> '...'`; если снова брак — в галерею с пометкой «не собрался».
2. Собери **одну общую галерею** — автономный HTML-файл в `$BB_THREAD_STORAGE/reports/arena-<slug>.html` (каталог создай сам, инлайн CSS/JS):
   - Шапка: бриф, дата, участники, счёт вариантов.
   - Группировка по агентам: полоса Claude Fable / Claude Opus / Codex / GLM 5.3, у каждого — его фирменный цвет (Claude Fable `#C15F3C`, Claude Opus `#8C4426` — в тёмной теме `#E39C77`, Codex `#0E7490`, GLM `#7C3AED` — в тёмной теме `#A78BFA`).
   - Каждый вариант — вкладка/карточка: название, «в чём ставка» (из notes.md агента), живой прототип в iframe. Содержимое вариантов **инлайнь через `srcdoc`** — так галерея остаётся одним самодостаточным файлом.
   - Секция «Сравнение от организатора»: что общего у подходов, чем принципиально различаются, сильная сторона каждого агента, твоя рекомендация топ-3 (по вариантам, не по агентам).
   - Отдельная строка **«Fable vs Opus»**: чем различаются решения двух Claude (модели близки по качеству — различия показательны). Если почти идентичны — так и напиши.
   - Полный ответ/заметки каждого агента — в модальном окне по клику (`<dialog>` + `showModal()`, закрытие по ✕, фону и Esc), не в узкой колонке.
3. Покажи галерею прямо в чате директивой inline-vis (отдельным блоком, НЕ внутри код-блока):

```text
::inline-vis{source="thread-storage" file="reports/arena-....html"}
```

Локальные файлы остаются в песочницах — это резерв и материал для внедрения.
4. В чат — короткая сводка: сколько вариантов, от кого, твой топ-3 одной строкой каждый. Подскажи Илье, что участники висят дочерними тредами — в каждого можно заглянуть.

## Шаг 6. Выбор и внедрение

Илья отвечает свободно: «беру вариант 7», «скрести 3 и 11», «все мимо».
- Победитель/микс → дорабатывай итерациями, обновляя **тот же файл галереи**. Победитель — первая вкладка «Финал», остальные сворачиваются в «Архив».
- Просит внедрить в продукт → это уже обычная разработка: перенеси победителя в проект сам, одним агентом, по правилам проекта.
- Все мимо → разбери фидбек и вернись к Шагу 3 с новыми направлениями, не полируй мусор.

## Модели (фронтир + максимальный ризонинг)

Без явных флагов BB берёт дефолтную модель провайдера — после обновления дефолт может съехать. Поэтому фиксируем модель и ризонинг явно (таблица в Шаге 4). У Codex максимум — `xhigh`.

**Проверять после обновлений:**

```bash
bb provider models codex --environment "$BB_ENVIRONMENT_ID"
bb provider models claude-code --environment "$BB_ENVIRONMENT_ID"
bb provider models acp-opencode --environment "$BB_ENVIRONMENT_ID"
```

Появилась более свежая модель — обнови таблицу здесь и в bb-council.

## Обработка проблем

- **Spawn упал «не авторизован» / «лимит»**: продолжай с оставшимися, отметь в галерее. Логин делает Илья: `codex login` / `claude` в терминале. GLM идёт через opencode (`acp-opencode`): если недоступен — проверь, что opencode настроен с Z.AI Coding Plan.
- **Тред участника завис**: `bb thread stop <id>`, затем свежий spawn того же участника.
- **Ретрай по окну лимитов**: BB сам ждёт и повторяет — `bb provider-retry status`, не пересоздавай тред.
- **Агент вышел за песочницу** (создал файлы не там): перенеси файлы в его папку, в следующий раз ужесточи формулировку ограничения в промпте.
- **Вариант с внешними CDN**: попроси того же агента переделать на инлайн (`bb thread tell`) или почини сам, если правка тривиальна.
